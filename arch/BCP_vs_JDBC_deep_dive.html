BCP vs JDBC — Deep Dive

T24 Init Load · Spark on Kubernetes · So sánh kỹ thuật 2 phương pháp extract

1. Tổng quan

Khi cần extract hàng chục triệu dòng từ SQL Server về MinIO (Parquet), có 2 lựa chọn: BCP (Bulk Copy Program — tool native của Microsoft) và Spark JDBC (đọc qua JDBC driver, chia partitions). Cả hai đều cho ra cùng kết quả: file Parquet trên MinIO. Nhưng cách đi khác nhau hoàn toàn — dẫn đến tốc độ và resource usage khác nhau.


BCP — Bulk Copy
✅ Native protocol của SQL Server
✅ 1 connection, stream liên tục
✅ Không qua query planner
✅ 0 executor pod — nhẹ cluster
✅ ~25s / 100K rows
⚠️ Shared lock khi chạy
VS
JDBC — Spark JDBC
❌ Generic protocol, đa năng
❌ N connection song song
❌ Query plan × N partitions
❌ 2 executor pod — nặng hơn
❌ ~68s / 100K rows
✅ Không giữ shared lock lâu

2. Luồng BCP — Chi tiết

Nguyên lý cốt lõi BCP dùng TDS Bulk Copy Protocol — giao thức riêng của Microsoft thiết kế 1 mục đích duy nhất: move data khối lớn. SQL Server tự push stream liên tục, không cần client hỏi từng batch.

Các bước thực hiện

1
Spark driver pod khởi động — chạy t24_bcp_extract.py
Không có executor. Chỉ 1 pod: 1 core, 2GB RAM.
subprocess.Popen(["bcp", "SELECT * FROM dbo.FBNK_CATEG_ENTRY", "queryout", ...])
2
BCP mở 1 connection TCP đến SQL Server
Handshake TDS 1 lần duy nhất. SQL Server kích hoạt Bulk Copy Engine — code path riêng, bypass query optimizer thông thường.
3
SQL Server bắt đầu scan disk tuần tự (sequential scan)
Đọc từ page đầu tiên đến page cuối cùng — không skip, không random access. Đây là pattern I/O nhanh nhất với SSD/HDD.
4
Stream binary liên tục — không round-trip
SQL Server push block liên tục qua TCP. BCP process nhận ngay, không cần gửi "next" request. 0 khoảng chờ giữa các block.
stream: [block_1][block_2][block_3]...[block_N] ← liên tục không ngắt
5
Filter stdout → pyarrow → Parquet → MinIO
BCP stdout pipe qua grep (lọc dòng status) → pyarrow đọc chunk → encode Parquet → upload MinIO. RAM chỉ giữ 1 chunk tại 1 thời điểm.
bcp stdout | grep -aP "\t" | pyarrow.open_csv() → write_parquet() → s3a://raw/test_bulk/

3. Luồng JDBC — Chi tiết

Nguyên lý cốt lõi JDBC là generic protocol — thiết kế cho mọi loại query. Spark phải chia bảng thành N partitions, mỗi executor tự query 1 range. Mỗi batch phải xin thêm từ server — tạo ra hàng nghìn round-trip.

Các bước thực hiện

1
Spark driver tính partition boundaries
Driver query min/max của partition column → chia thành N range. 2 executor → 2 partitions.
Partition 1: WHERE id BETWEEN 0 AND 40,000,000 Partition 2: WHERE id BETWEEN 40,000,001 AND 80,000,000
2
Spin up 2 executor pods
Mỗi executor: 2 core + 2GB RAM. Tổng thêm 4 core + 4GB RAM so với BCP.
3
Mỗi executor mở 1 connection riêng — gửi query
SQL Server nhận 2 query đồng thời, tạo 2 query plan, 2 cursor, scan 2 range song song. Buffer pool bị hit từ 2 hướng.
4
Request-response loop — lặp hàng nghìn lần
Executor nhận batch → xử lý xong → gửi "next" → chờ server → nhận tiếp. Mỗi batch 10,000 rows → 4,000 round-trip per executor.
[xin batch] → [chờ] → [nhận 10K rows] → [deserialize] → [xin batch] → [chờ] → ...
5
Deserialize từng row qua nhiều tầng
Mỗi row: SQL Server value → TDS binary → JDBC ResultSet → Java Object → Spark InternalRow → Parquet. Tốn CPU gấp nhiều lần BCP.
ResultSet.next() → getObject() → InternalRow → UnsafeRow → Parquet encoder

Resource BCP JDBC Winner
Spark pods 1 driver pod 1 driver + 2 executor pods BCP

CPU (Spark) ~1 core · gần idle ~5 core (1 + 2×2) BCP 5×
CPU (DB) Thấp — 1 scan, bulk engine Cao hơn — N query plan, N cursor BCP
Disk I/O (DB) Sequential scan 1 lần N range scan song song BCP

Bottleneck Disk I/O + Network CPU deserialize + round-trip —
Lưu ý về Lock BCP giữ shared lock toàn bảng trong suốt quá trình export (~30–45 phút với 80M rows). Mọi INSERT/UPDATE từ T24 sẽ bị block. Giải pháp: chạy sau COB ngoài giờ hành chính, hoặc dùng WITH (NOLOCK) (chấp nhận dirty read, CDC sẽ bù sau).

6. Tại sao BCP nhanh hơn — 3 lý do cốt lõi

Lý do 1 — Protocol native vs generic

JDBC path (5 tầng): SQL Server value → TDS encoding → JDBC driver decode (Java) → Java Object (ResultSet) → Spark InternalRow → Parquet encoder → MinIO BCP path (2 tầng): SQL Server value → TDS binary stream (native) → pyarrow decode + Parquet → MinIO

Mỗi tầng serialize/deserialize tốn CPU và memory copy. BCP ít tầng hơn = ít overhead hơn × 80,000,000 rows.

Lý do 2 — 0 round-trip vs 8,000 round-trip

JDBC — mỗi batch 10K rows phải xin thêm: [xin]──chờ──[nhận]──[xin]──chờ──[nhận]──[xin]──chờ──[nhận]── × 4,000 lần per executor ↑↑↑ ↑↑↑ ↑↑↑ latency latency latency ← thời gian lãng phí BCP — server tự push, không cần hỏi: [kết nối 1 lần]──████████████████████████████████████████── done ↑ stream liên tục, 0 khoảng dừng ↑

Lý do 3 — Sequential I/O vs Random I/O

BCP — 1 scan từ đầu đến cuối: Disk: [Page 1][Page 2][Page 3][Page 4]...[Page N] ← sequential, nhanh nhất ──────────────────────────────────────────► JDBC — 2 executor scan 2 range song song: Disk: [Page 1] [Page N/2] ──────────────► ──────────────► ← 2 luồng cùng lúc Exec 1 Exec 2 → disk phải phục vụ 2 vị trí đồng thời → overhead seek

7. Khi nào dùng BCP, khi nào dùng JDBC?

Tình huống Dùng BCP Dùng JDBC
Init load hàng chục triệu rows ✅ Tốt hơn nhiều ❌ Chậm, tốn resource
Extract incremental (vài nghìn rows) ⚠️ Overhead setup lớn ✅ Nhanh hơn cho data nhỏ
Chạy trong giờ hành chính ❌ Shared lock block T24 ✅ Row-level lock, ít ảnh hưởng
SQL Server không có mssql-tools ❌ Không dùng được ✅ Chỉ cần JDBC driver
Complex WHERE / filter trước extract ⚠️ Được nhưng không tối ưu ✅ Query plan tối ưu filter
Cluster ít resource (RAM/CPU) ✅ Chỉ cần 1 pod nhỏ ❌ Cần executor pods
Quyết định trong project này Init load T24 → BCP. 5 bảng × ~80M rows prod → BCP nhanh hơn ~2.7× và nhẹ cluster hơn ~3×. Chạy sau COB, ngoài giờ hành chính, với NOLOCK + CDC bù gap sau.
